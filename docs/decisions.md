# 設計判断の記録

未決の論点を決めた内容と理由を残す。状態は「確定」「暫定」「未決」のいずれか。

> 出典: 課題の原文（利用者が貼り付けた「FY26 長期インターン オンボーディング課題」）。
> リポジトリ上の README は取得できていないため、原文との差異があれば原文を正としてここを直す。

## 1. 仕訳行の形

- 状態: **暫定**（メンターまたは利用者との相談後に確定する）
- 暫定案: 1行に借方（勘定科目＋金額）と貸方（勘定科目＋金額）の両方を持たせる。片側は空でもよい。
- 食い違いの内容（原文内）:
  - 「データ定義」: 仕訳行は借方勘定科目・借方金額・貸方勘定科目・貸方金額を持つ。科目と金額は、それぞれ片方がある場合にもう片方が必須。例では「仕訳行１」の中に借方現金100円/貸方普通預金50円と、借方空/貸方定期預金50円が並ぶ。
  - 「仕訳登録機能」: 仕訳行の登録項目は摘要・貸借区分・勘定科目・金額で、1行が片側だけの形に読める。
- 暫定案の理由: データ定義の例をそのまま表現できる。借方と貸方が多対多で対応する仕訳も扱える可能性を残せる。
- 影響: テーブル設計、バリデーション、フォームUIがすべて変わる。確定するまで設計書1以降は暫定扱いにする。

## 2. 勘定科目の削除ポリシー

- 状態: **確定**
- 決定: 仕訳行で使用中の勘定科目は削除できない（原文の例A）。外部キーは `RESTRICT`、API は 409 とエラーコードを返す。
- 理由: 過去の仕訳が参照する科目を消すと、仕訳の貸借が崩れて記録が壊れる。会計データを黙って消さない方を選ぶ。

## 3. 貸借一致チェック

- 状態: **確定**
- 決定: 仕訳の登録・編集時に、仕訳全体で借方合計と貸方合計が一致しなければ 400 を返す。フィールド単位のエラーとして返す。
- 検証の単位: 行ごとではなく仕訳全体。原文の例は、行1が借方100円/貸方50円で行単位では不一致だが、仕訳全体では借方100円＝貸方50円＋50円で一致する。
- 理由: 原文に明記はないが、例は仕訳全体で一致している。会計として自然で、domain のテスト題材にもなる。
- 補足: フロントでも同じ検証を行うが、サーバー側の検証を正とする。

## 4. 編集時の仕訳行の更新方式

- 状態: **確定**
- 決定: 全置換。保存時に既存の仕訳行を削除し、送られた行を入れ直す。
- 理由: 行の追加・削除・更新を同じ処理で扱え、実装とテストが単純になる。代償として仕訳行 ID は保存のたびに変わるため、行 ID を外部から参照しない前提にする。

## 5. 勘定科目の貸借区分の扱い

- 状態: **確定**
- 決定: 勘定科目マスタの属性として保持・表示するだけにする。仕訳行で借方・貸方のどちらに使えるかは制約しない。
- 理由: 実務でも科目は両側に現れうる。制約すると例の仕訳の成立が科目の区分に依存する。

## 6. domain モデルと DB のレコードの分離

- 状態: **確定**
- 決定: 分ける。domain は DB に依存しない純粋な Kotlin のクラスにし、jOOQ の生成クラスは `infrastructure/` に閉じ込めて、Repository の実装側で相互に変換する。
- 理由: 学習目的。レイヤ間の依存方向（Controller → Usecase → Domain / Repository）と、domain を DB なしでテストできる形を実際に体験する。
- 代償: 変換コードとそのテストが増える。小規模な課題では過剰になりうることを承知のうえで選ぶ。
- 経緯: 当初は JPA エンティティとの分離として決めた。永続化技術を jOOQ に変えたため（論点 8）、対象を jOOQ の生成クラスに読み替えた。

## 7. 一覧まわり

- 状態: **確定**
- 決定:
  - 表示順: 仕訳一覧は取引日の降順。同じ取引日の仕訳は ID の降順。
  - ページング: なし。全件を 1 画面に表示する。
  - 操作後の遷移: 登録・編集・削除の成功後は一覧に戻る。
- 理由: 課題の性能要件は N+1 の回避であり、ページングは要求されていない。ページングなしなら仕訳と仕訳行をまとめて取得でき、設計書とテストも単純になる。操作後に一覧へ戻せば、一覧への即時反映という要件を満たす。
- 見直す条件: 件数が増えて一覧が重くなった場合は、ID 一覧を先に取り、続けて詳細を取る 2 段階クエリでページングを入れる。

## 8. 永続化技術は jOOQ

- 状態: **確定**（jOOQ のライセンス条件と最新バージョンは着手時に確認する）
- 決定: JPA ではなく jOOQ を使う。スキーマは Flyway のマイグレーションを正とし、そこから jOOQ のコードを生成する。
- 理由:
  - 発行される SQL を自分で書いて把握でき、一覧のクエリ本数（N+1 回避）を設計どおりに作れる。
  - 編集時の全置換（論点 4）も、行の削除と一括追加としてそのまま書ける。
  - プロダクトの tequila_web も jOOQ と Flyway を使っており（同リポジトリの `.claude/playbook.md` の R-010）、課題の目的である「プロダクトで使う技術に慣れる」に合う。
- 代償:
  - コード生成をビルドに組み込む設定が必要になる。
  - 仕訳と仕訳行の保存（仕訳を insert して ID を取り、続けて仕訳行を insert する）を自分で書く。
- 影響:
  - Spring Data のインターフェースは使わない。Repository のインターフェースの置き場所は、アーキテクチャ設計書で決める。
  - ライブラリ候補から JPA 関連を外し、jOOQ とそのコード生成を入れる。
- 確認事項: 課題の技術スタック指定はライブラリを縛っていないが、メンターに一言確認する。
